===== PART (a) : WHY STABILITY IS WHAT MAKES MULTI-KEY SORTING WORK =====

  Requirement: order the queue by tier, and alphabetically by name inside
  each tier. The standard technique is two passes over a SINGLE key each:
      pass 1: sort by the LEAST significant key (name)
      pass 2: sort by the MOST  significant key (tier)
  Pass 2 must not disturb the work of pass 1, which requires stability.

  Required order (reference)     : P1:Siti Nurh  P1:Wong Mei   P2:Chan Kok   P2:Chua Li T  P2:Kavitha R  P2:Muthu Sam  P3:Ahmad Fai  P3:Lim Hui L  P3:Nurul Ais  P3:Sharifah   P3:Tan Wei M  P3:Teo Seng   P4:Goh Jia H  P4:Ong Boon   P4:Raj Kumar  P4:Yusof Bin  

  Two stable passes              : P1:Siti Nurh  P1:Wong Mei   P2:Chan Kok   P2:Chua Li T  P2:Kavitha R  P2:Muthu Sam  P3:Ahmad Fai  P3:Lim Hui L  P3:Nurul Ais  P3:Sharifah   P3:Tan Wei M  P3:Teo Seng   P4:Goh Jia H  P4:Ong Boon   P4:Raj Kumar  P4:Yusof Bin  

  Two unstable passes            : P1:Siti Nurh  P1:Wong Mei   P2:Kavitha R  P2:Muthu Sam  P2:Chan Kok   P2:Chua Li T  P3:Sharifah   P3:Tan Wei M  P3:Teo Seng   P3:Nurul Ais  P3:Ahmad Fai  P3:Lim Hui L  P4:Yusof Bin  P4:Goh Jia H  P4:Ong Boon   P4:Raj Kumar  

  Stable pipeline matches the requirement   : YES

  The unstable pipeline is not merely untidy - it silently produces the
  WRONG report, while still looking correctly sorted by tier. This is the
  same property radix sort depends on in part (b): it is a chain of single-
  digit passes, and it is correct only because each pass is stable.

===== PART (b) : NO COMPARISON SORT CAN BEAT Omega(n lg n) =====

  A comparison sort only ever asks 'is a < b?'. Its whole execution is a path
  down a binary decision tree whose leaves are the possible orderings. There are
  n! orderings, a binary tree of height h holds at most 2^h leaves, so
        2^h >= n!  =>  h >= lg(n!) = n lg n - n lg e + O(lg n) = Omega(n lg n).

  Below, every one of the n! input permutations is actually sorted and the
  worst comparison count is recorded. No algorithm dips below the bound.

   n          n!     lower bound      merge sort    insertion sort     selection   bound ok?
                     ceil(lg n!)           worst             worst         worst
   2           2               1               1                 1             1         yes
   3           6               3               3                 3             3         yes
   4          24               5               5                 6             6         yes
   5         120               7               8                10            10         yes
   6         720              10              11                15            15         yes
   7        5040              13              14                21            21         yes
   8       40320              16              17                28            28         yes

  THE CONDITION under which the bound holds: the algorithm may learn about the
  keys ONLY by comparing them pairwise. Nothing is assumed about what a key is.
  Lift that restriction - allow the algorithm to look INSIDE a key, at its digits
  - and the decision tree stops being binary, the argument collapses, and linear
  time becomes possible. That is exactly what radix and counting sort do.

===== PART (b) : IS RADIX SORT REALLY FASTER THAN O(n lg n)? =====

  Keys are COE-style bid amounts in [0, 999999].
  Radix is run at two radices, because the choice of base is the whole story:
      base 10  -> d = 6 passes  (human-readable digits, used in the COE demo)
      base 256 -> d = 3 passes  (what a real implementation would use)
  Every pass is a full streaming pass over the array, so halving the pass count
  roughly halves the running time while leaving the complexity Theta(d(n+k)).
  A Theta(n) algorithm has constant time/n; a Theta(n lg n) one does not.

         n   radix256(ms)   radix10(ms)  std::sort(ms)  mergesort(ms)  radix256 ns/n   std::sort ns/n
     50000           0.28          3.31           3.49           3.87            5.6             69.7
    100000           0.52          6.45           6.70           7.84            5.2             67.0
    200000           1.06         12.80          12.57          17.06            5.3             62.9
    400000           2.65         25.29          25.48          35.63            6.6             63.7
    800000           5.25         50.17          55.77          73.92            6.6             69.7
   1600000          11.36        101.98         114.54         157.70            7.1             71.6
   3200000          21.18        199.03         235.25         325.34            6.6             73.5

  Radix base 256 is about an order of magnitude faster than std::sort right
  across the range, and roughly 14x faster than the merge sort.

  BUT READ THE ns/n COLUMNS HONESTLY. std::sort's ns/n does climb, as its lg n
  factor predicts - but radix's climbs by a similar factor, even though radix is
  Theta(n) and its ns/n should be flat. The reason is the memory hierarchy: over
  50k..3.2M the array grows past every level of cache, and radix's scattered
  writes suffer for it. Meanwhile lg n only rises from 15.6 to 21.6 over that
  same range - a factor of 1.4 - so the asymptotic gap that SHOULD widen is the
  same size as the cache effect masking it. Wall-clock timing simply cannot
  settle this question at these sizes. Menu option 6 settles it by counting
  operations instead, which no cache can distort.

  The radix10 column is the other caveat. Both radices are Theta(n), yet doubling
  the pass count from 3 to 6 costs roughly 9x in wall-clock time, leaving base-10
  radix level with a cache-friendly introsort. Theta(n) is a statement about
  growth, not a promise of being fastest; the constant hidden in d(n+k) is large
  and real. The table below finds the point where it stops being worth paying.

  --- THE LIMITATION : RADIX PAYS FOR KEY WIDTH ---
  Theta(d(n+k)) is linear only while d is small. Widening the key at fixed n
  adds passes, and radix eventually loses to a comparison sort.

===== PART (b) : THE CACHE-FREE PROOF - COUNTING OPERATIONS =====

  Wall-clock time mixes the algorithm together with the memory hierarchy. Basic
  operation counts do not, so this is where the asymptotic claim is settled:
      radix     Theta(d(n+k)) with d,k fixed  =>  ops/n must be CONSTANT
      mergesort Theta(n lg n)                 =>  cmps/n must GROW like lg n

         n     radix ops       ops/n      merge cmps      cmps/n     cmps/(n lg n)
     25000        150765      6.0306          334065     13.3626            0.9146
     50000        300765      6.0153          718141     14.3628            0.9201
    100000        600765      6.0076         1536590     15.3659            0.9251
    200000       1200765      6.0038         3272581     16.3629            0.9292
    400000       2400765      6.0019         6946060     17.3651            0.9331
    800000       4800765      6.0010        14690442     18.3631            0.9364
   1600000       9600765      6.0005        30983689     19.3648            0.9396
   3200000      19200765      6.0002        65164902     20.3640            0.9424

  This is the proof the brief asks for, and it is exact rather than measured:
    radix ops/n is CONSTANT across a 128-fold increase in n  ->  Theta(n)
    merge cmps/n GROWS, while cmps/(n lg n) settles          ->  Theta(n lg n)
  Radix sort therefore performs asymptotically fewer operations than any
  comparison sort can, which is exactly what the Omega(n lg n) bound forbids a
  comparison sort from doing - and it is allowed to, because it never compares
  two keys with each other.
